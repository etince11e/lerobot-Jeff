# 异步 IK 遥操作延迟修复说明

## 1. 变更概述

本次修改针对 `rebot_rs_follower` 遥操作链路中“同步 IK 阻塞主控制循环”的问题进行修复。

本次只改动 IK 调度方式，没有修改机器人观测线程，也没有修改主循环中“先读取观测、后读取手柄”的执行顺序。

修复后的核心行为是：

```text
遥操作线程
    ├─ 读取 Pico 手柄
    ├─ 转换 TCP 目标
    ├─ 覆盖 latest-only IK 请求
    └─ 立即返回，不等待 IK

IK 工作线程
    ├─ 取出最新 TCP 目标
    ├─ 使用独占的 Pinocchio Data 执行 IK
    ├─ 同一遥操 epoch 内发布每个成功结果
    ├─ 只保留尚未开始计算的最新请求
    └─ 只有跨 epoch 的结果才会被丢弃

500 Hz 电机控制线程
    └─ 持续发送最近一次有效的关节目标
```

## 2. 原始问题

原来的 `send_action()` 在遥操作主线程中直接调用 IK：

```python
target = self._action_to_target(action)
result = self._sdk.solve_ik(...)
self._q_target = result.q
```

这意味着每帧遥操作都必须等待完整 IK 计算结束后，才能返回主循环。

当 IK 计算时间超过当前控制周期时，会产生以下现象：

1. 主循环无法维持设定的 30/60 Hz。
2. 下一次 Pico 手柄数据不能按时采样。
3. 手柄快速改变方向时，机械臂仍在等待上一帧 IK。
4. 如果 IK 失败，旧代码会保持上一次关节目标，表现为短暂卡住。
5. 如果简单地使用 FIFO 队列，会把过时的手柄动作逐个执行，形成明显拖尾。

因此，本次修改没有采用普通的生产者/消费者队列，而是采用“只保留最新请求”的 mailbox 设计。

## 3. 修改动机

### 3.1 为什么使用独立 IK 线程

RS 电机控制线程必须持续运行，不能因为某次 IK 计算时间变长而停止发送指令。

将 IK 移到独立线程后：

- 遥操作线程不会等待 IK；
- 电机控制线程仍然可以按 SDK 配置的高频率发送关节指令；
- IK 计算速度低于手柄采样速度时，不会拖慢手柄采样；
- 可以明确统计 IK 耗时和过期结果数量。

### 3.2 为什么不使用无限 FIFO 队列

遥操作目标具有“最新状态优先”的特点，而不是必须逐条执行的离散事件。

例如操作者连续产生目标 `A → B → C`，如果 `A` 的 IK 计算期间已经收到了 `C`，此时继续执行 `A` 和 `B` 没有意义，反而会让机械臂落后于操作者。

因此使用单槽请求：

```text
旧请求 A  ← 被新请求 B 覆盖
旧请求 B  ← 被新请求 C 覆盖
当前只计算 C
```

### 3.3 为什么需要区分请求序号和 IK epoch

最初的实现使用 `_ik_request_seq` 同时表示“输入请求顺序”和“结果是否仍然有效”。
这对普通异步任务可以成立，但对连续遥操作过于激进：如果 A 正在计算时 B 到达，A 完成后会因为序号变化而被丢弃。

当 IK 耗时大于 Pico 输入周期时，可能出现所有结果都被丢弃、机器人持续发送旧 `_q_target` 的情况。

因此现在把两个语义拆开：

因此每个请求都带有递增序号：

```text
正常 Pico 输入:
请求 A: seq=1, epoch=5
请求 B: seq=2, epoch=5

回零/复位:
请求 C: seq=3, epoch=6
```

`request_seq` 只用于描述输入顺序和统计，不再用于丢弃同一遥操 epoch 内已经完成的结果。

`ik_epoch` 用于生命周期失效边界。只有回零、复位、控制模式切换、断开等操作使 epoch 改变后，旧 epoch 的 IK 结果才会被丢弃。

## 4. 具体修改内容

### 4.1 新增异步 IK 状态

在 `RebotRSFollower.__init__()` 中新增：

```python
self._ik_condition = threading.Condition()
self._ik_request: tuple[int, int, object] | None = None
self._ik_request_seq = 0
self._ik_epoch = 0
self._ik_stop_requested = False
self._ik_thread: threading.Thread | None = None
self._ik_worker_seed = np.zeros(6, dtype=np.float64)
```

这些状态分别用于：

| 状态 | 作用 |
|---|---|
| `_ik_condition` | 唤醒和停止 IK 线程，避免轮询 sleep |
| `_ik_request` | 保存唯一一个待处理的最新请求 |
| `_ik_request_seq` | 标识输入顺序，不单独决定结果是否失效 |
| `_ik_epoch` | 标识回零、复位、断开等生命周期边界 |
| `_ik_stop_requested` | 请求线程退出 |
| `_ik_thread` | 保存 IK worker 线程句柄 |
| `_ik_worker_seed` | 保存最近一次成功 IK 的 warm-start 关节配置 |

另外增加了两个调试统计字段：

```python
self._last_ik_duration_s
self._ik_dropped_results
```

它们分别记录最近一次 IK 耗时和被丢弃的过期 IK 结果数量。

### 4.2 连接时启动 IK worker

硬件、模型、控制线程和相机全部准备完成后，才启动 IK worker：

```python
self._connected = True
self._start_ik_worker()
```

这样可以避免 IK 线程在 SDK、Pinocchio 模型或电机组尚未初始化完成时收到请求。

### 4.3 `send_action()` 改为非阻塞提交

修改后的 `send_action()` 不再包含 `solve_ik()`。

它现在执行以下步骤：

1. 检查 action 字段是否完整；
2. 将 TCP 位姿转换为 IK 目标；
3. 递增请求序号；
4. 用新请求覆盖旧请求；
5. 立即更新夹爪目标；
6. 立即返回原始 action。

核心代码逻辑如下：

```python
with self._ik_condition:
    self._ik_request_seq += 1
    self._ik_request = (self._ik_request_seq, target)
    self._ik_condition.notify()
```

这里的 `notify()` 只负责唤醒 IK worker，主遥操作线程不会等待求解完成。

### 4.4 IK worker 独占 Pinocchio Data

IK worker 从 mailbox 取得最新请求后：

1. 在锁保护下复制 `_ik_worker_seed`；
2. 取得模型、Pinocchio Data、末端帧和关节组引用；
3. 在当前线程调用 `solve_ik()`；
4. 记录求解耗时；
5. 更新 worker 的 warm-start seed；
6. 检查请求 epoch；
7. 同一 epoch 内发布成功的 `_q_target`，跨 epoch 的结果才丢弃。

Pinocchio 的 `Data` 只在 IK worker 中用于求解，避免多个线程同时操作同一个求解缓存。

### 4.5 同 epoch 结果发布与跨 epoch 结果丢弃

连续遥操作时，新请求到达并不代表正在计算的结果无效。

例如：

```text
t=0 ms:   开始 IK(A)
t=16 ms:  B 到达，mailbox 保存 B
t=25 ms:  IK(A) 完成，发布 A
t=25 ms:  worker 开始 IK(B)
```

如果 A、B、C、D 在 A 计算期间到达，mailbox 最终只保留 D，但 A 仍然可以先发布：

```text
输入:  A B C D E F
求解:  A A A A → D D D D → F F F F
输出:  A       → D       → F
```

结果发布只检查 epoch：

```python
with self._ik_condition:
    if request_epoch != self._ik_epoch:
        self._ik_dropped_epoch_results += 1
        continue

    with self._target_lock:
        self._q_target = q_goal
        self._q_seed = q_goal.copy()
        self._ik_worker_seed = q_goal.copy()
```

同一 epoch 内，即使存在更新的 mailbox 请求，也会先发布已完成结果，然后继续求解 mailbox 中的最新请求。

这样可以避免旧实现中的“结果全部 stale、机器人持续保持旧位置”问题，同时仍然保留以下安全边界：

```text
IK worker 正在计算 epoch=5 的目标
    ↓
主线程开始回零，epoch 5 → epoch 6
    ↓
IK worker 计算完成，发现 epoch 不一致
    ↓
丢弃旧结果，不覆盖回零目标
```

epoch 检查和结果发布在同一个条件变量临界区中，因此回零操作不会在检查和写入之间插入。

### 4.6 IK 失败处理

异步 IK 仍然保持原有的安全策略：

- 单次 IK 失败时，保持最近一次有效关节目标；
- 记录失败日志；
- 不向电机发送非有限值；
- IK 线程异常不会直接阻塞遥操作主线程。

如果 IK 返回非有限关节值，也会丢弃结果并保持旧目标。

### 4.7 回零和启动位姿的保护

在显式的启动位姿或机械零点轨迹开始前，会调用 `_invalidate_ik_requests()`：

```python
self._ik_request = None
self._ik_epoch += 1
self._ik_request_seq += 1
```

这保证旧的手柄目标或正在计算的旧 IK 结果不能覆盖回零轨迹。

显式点到点动作结束后会再次清理 mailbox 并切换 epoch，避免回零期间到达的遥操请求在动作结束后立即覆盖新的目标。

### 4.8 断开时停止 IK worker

断开顺序修改为：

```text
标记不再连接
    ↓
停止并等待 IK worker
    ↓
停止反馈线程
    ↓
停止控制线程
    ↓
断开执行器和相机
```

这样可以避免 IK worker 在模型、Pinocchio Data 或 SDK 资源释放后继续访问它们。

## 5. 修改前后的数据流对比

### 修改前

```text
teleop.get_action()
    ↓
robot.send_action()
    ↓
solve_ik()        ← 阻塞遥操作线程
    ↓
_q_target 更新
    ↓
下一帧循环
```

### 修改后

```text
teleop.get_action()
    ↓
robot.send_action()
    ├─ 覆盖最新 IK 请求
    ├─ 更新夹爪目标
    └─ 立即返回

IK worker
    ├─ solve_ik()
    ├─ 更新 worker seed
    ├─ 检查 epoch
    └─ 发布同 epoch 的已完成 _q_target

500 Hz 控制线程
    └─ 持续发送最近一次有效 _q_target
```

## 6. 本次没有修改的内容

为了隔离变量，本次暂时没有修改：

1. `lerobot_teleoperate.py` 中的观测读取顺序；
2. 相机观测线程；
3. `joint_target_interpolation_time_s` 的默认值；
4. Pico4 端的速率限制；
5. Pico4 SDK 的多次读取方式；
6. 500 Hz 电机控制线程的发送策略。

因此，异步 IK 修复后仍可能存在其他延迟来源，尤其是关节插值和观测读取。

### 7.1 同 epoch 结果发布测试

测试先让请求 `first` 进入求解，再提交 `second`，确认：

- `first` 的结果先写入 `_q_target`；

## 8. 使用和调试建议

为了单独观察异步 IK 的改善效果，建议先暂时关闭关节目标插值：

```yaml
joint_target_interpolation_time_s: 0.0
```

之后再逐步测试：

```text
0.0 → 0.005 → 0.01 → 0.02
```

建议重点观察：

- `_last_ik_duration_s`：最近一次 IK 耗时；
- `_ik_dropped_results`：被生命周期失效丢弃的结果总数；
- `_ik_dropped_epoch_results`：跨 epoch 被丢弃的结果数量；
- 遥操作主循环实际频率；
- IK 失败日志出现频率；
- 手柄反向运动时机械臂的拖尾时间。

如果 IK 平均耗时仍然接近或超过手柄采样周期，下一步可以考虑降低 `ik_max_iter`、改用增量式 Jacobian IK，或将 IK 改为关节速度/关节增量控制。

## 9. 本次追加修正：放宽同 epoch stale 结果策略

后续审查发现，初版异步 IK 文档和实现都把“请求不是最新”当成了“结果已经失效”。这会在连续遥操中造成过于激进的结果丢弃：当 IK 耗时超过 Pico 输入周期时，可能连续丢弃 A、B、C 等已经完成的结果，导致电机线程长时间重复发送旧 `_q_target`。

本次追加修正后的规则是：

```text
未开始求解的旧 request：可以被 mailbox 中的新 request 覆盖
已经完成的同 epoch result：允许发布，并更新 worker seed
跨 epoch result：必须丢弃
```

对应代码调整包括：

1. `_ik_request` 从 `(seq, target)` 扩展为 `(seq, epoch, target)`；
2. 新增 `_ik_epoch`，将请求顺序和生命周期失效分开；
3. 移除同 epoch 的 `request_seq` stale 丢弃判断；
4. 新增 `_ik_worker_seed`，每次成功 IK 都更新 warm-start seed；
5. 回零、复位、结束显式点到点动作和断开时切换 epoch；
6. 新增同 epoch 发布测试和跨 epoch 丢弃测试。

这次修正不会消除 IK 本身的计算时间，但会避免“IK 结果全部被判 stale，机器人持续保持旧目标”的额外卡顿。异步 IK 的实际输入到关节目标延迟仍然包含 IK 求解时间、mailbox 等待时间、关节插值和电机跟随时间。
